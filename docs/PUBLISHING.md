# Publishing 0.2.0

0.2.0 is the first tagged release of a repository that already exists: the initial
snapshot (0.1.0) was pushed to `github.com/bjornhagstrom/ckanext-actor-registry` on
2026-09-18 with default branch `master`, without a release or tag. Steps 2 and 3 below
were done for that snapshot; for 0.2.0, update the repository with the reviewed contents
and continue with step 4.

This checklist separates creation of the public repository from submission to
the CKAN Ecosystem Catalog. The extension should live in its own Git repository;
it should not be submitted as code to the main `ckan/ckan` repository.

## 1. Final human review

- review every file in the release diff;
- confirm that no passwords, tokens, hostnames, personal data or deployment
  configuration are present;
- test a clean installation and `ckan db upgrade -p actor_registry`;
- create, edit and deactivate an actor and a contact point;
- create and edit a dataset using both selectors;
- verify authorization as sysadmin and ordinary user;
- verify RDF output if advertising the optional DCAT profile;
- accept the statements in `AI_ASSISTANCE.md` and the release notes.

## 2. Create the GitHub repository (done 2026-09-18)

Create a public repository named `ckanext-actor-registry` under the maintainer's
account or a stable organization. Do not initialize it with another README,
license or `.gitignore`, because those files already exist here.

Suggested GitHub description:

> Reusable actor and contact point registries for CKAN metadata, with Scheming widgets and optional DCAT serialization.

Suggested topics:

`ckan`, `ckan-extension`, `metadata`, `dcat`, `dcat-ap`, `foaf`, `vcard`,
`contact-points`, `publishers`

Enable Issues, Discussions and private vulnerability reporting. Set the default
branch to `main` and add branch protection after the initial import.

## 3. Import this directory as a standalone repository (done for 0.1.0; repeat the update for 0.2.0)

Copy only the contents of `ckanext-actor-registry` into the new repository. The
`OWNER` and `REPOSITORY_URL` placeholders in the documentation were replaced when
the repository was created; check that no new ones were added. Keep deployment
files and the wider CKAN portal out of the repository.

Make the first commit with a factual message such as:

> Prepare ckanext-actor-registry 0.2.0 alpha

The commit author should be the human maintainer. AI tools should not be added as
co-authors; the repository-level disclosure records their assistance.

## 4. Create the release

After a clean-install check (run `examples/ckan-2.12` and its `smoke_check.py` on CKAN
2.11 and 2.12), replace `Unreleased` on the 0.2.0 changelog heading with the release date.
Tag the reviewed commit `v0.2.0` and create a GitHub release titled:

> ckanext-actor-registry 0.2.0 — alpha

Use `docs/RELEASE_NOTES_0.2.0.md` as the release body and mark it as a
pre-release. Attach source archives automatically generated by GitHub; binary
artifacts are not required.

## 5. Ask the CKAN community for feedback

Post `docs/CKAN_COMMUNITY_ANNOUNCEMENT.md` as a discussion in the CKAN community
after replacing `REPOSITORY_URL`. This is both an announcement and a final prior-
art check. If the community identifies a maintained equivalent, compare scopes
before asking users to adopt another package.

## 6. Submit to the CKAN Ecosystem Catalog

Use the current **Submit to Catalog** flow at `https://ecosystem.ckan.org/` and
copy the reviewed values from `docs/ECOSYSTEM_CATALOG_SUBMISSION.md`. The old
`extensions.ckan.org` GitHub repository is archived and should not be used for a
new pull request.

## 7. Package index publication later

PyPI publication is optional for 0.x. A GitHub release is sufficient for early
testing. Publish to PyPI only after adding a modern build configuration,
validating source and wheel contents, and confirming ownership of the package
name. Never upload from an environment containing unrelated credentials.
